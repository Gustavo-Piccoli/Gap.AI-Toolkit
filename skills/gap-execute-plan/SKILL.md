# Plan Executor

Execute a plan file generated by `/gap-create-plan`. The plan is the single source of truth: it was debated and approved by the user in a previous session, so your job is disciplined execution, not re-planning.

## 1. Validate the plan

- Locate the plan file the user passed (default location: project root, `plano-*.md`). If no file was given and exactly one `plano-*.md` exists at the root, confirm with the user before using it; if several exist, ask which one.
- Verify the file exists, is readable, and contains at minimum: Executor Persona, Context, Objective, Master Checklist, and Acceptance Criteria.
- If the file is missing, corrupted, or structurally broken, stop and inform the user. Never improvise a plan from a broken file — a bad execution is worse than no execution.

## 2. Detect fresh run vs. resume

Read the Master Checklist. If any items are already checked (`- [x]`), this is a resumed run: state in one short message what is already done, then continue from the first unchecked item. Do not redo completed work.

## 3. Execute

- Assume the Executor Persona defined in the plan for the entire execution.
- Work through the Master Checklist strictly in order, respecting the Context, the Constraints & Non-Goals, and any plan-specific directives in section 5 of the plan.
- **Minimal verbosity**: keep responses and reasoning short and dense — this preserves the user's tokens and credits for the actual work. Do not narrate routine steps or add courtesy filler. Report only decisions, blockers, and completions.
- **Live progress tracking**: immediately after completing each task, edit the plan file to mark its checkbox (`- [x]`). The plan file is the living record of progress; keeping it current is what makes interrupted runs resumable.
- **Stay in scope**: execute what the plan says. If the plan is ambiguous on some point, or reality contradicts it (e.g. a file it references does not exist), stop that task and ask the user (via `AskUserQuestion` in Claude Code / `ask_question` in Antigravity or direct chat). Never silently improvise beyond the plan's scope — the plan was approved as written, and unapproved work violates that approval.
- **Task failures**: if a task fails (failing test, broken build, command error), attempt to fix it within the plan's scope and constraints. If fixing it would require going beyond the scope or changing decisions the plan already settled, stop and ask the user before proceeding. Do not mark a task as done while it is failing.

## 4. Agents

- Dispatch the plan's Agent Tasks (section 7) as subagents (via `Agent` tool in Claude Code / `invoke_subagent` in Antigravity), in parallel whenever they are independent of each other.
- Model: best available Sonnet, effort High (in Claude Code) or inherited/specified model (in Antigravity).
- Give each agent exactly the standalone instruction and checklist defined in the plan, and require the return format the plan specifies.
- Coordinate actively: keep a record of what each agent must do, verify each agent's return against its checklist, mark the corresponding items in the plan file, and only then remove the task from pending work.
- Agents inherit the minimal-verbosity rule: instruct them to work and report with reduced verbosity.

## 5. Final review

After all phases of the Master Checklist are complete:

- Review every artifact produced (code, files, configs) against the Acceptance Criteria, marking each criterion in the plan file as it is verified.
- Fix any divergence found and re-verify.
- If the execution changed the project's structure, architecture, or conventions and a `CLAUDE.md` exists at the root, update its affected sections so it reflects the new state — otherwise the next plan creation will start from stale information.
- Close with a short report: what was done, the status of each acceptance criterion, and anything left pending with the reason.
